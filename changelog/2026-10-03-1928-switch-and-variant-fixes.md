### 调整 · 测试数据的体积估算改为生成时累加（2026-10-03）

### 优化 · 左侧栏乐谱列表接入虚拟化（2026-10-03）

- 现象：开发面板能造出上千首乐谱，而侧栏「乐谱列表」是全量渲染 —— 1000 首就是 1000 张 `SongCard`，
  每张还挂着跑马灯 / 波纹 / `v-scroll-into-view` 三套指令与各自的观察器。列表滚动与切换排序方式都明显
  掉帧，节点数还随乐谱数线性增长。
- 修法：新增通用能力 `useVirtualRows`（`platform/composables`，与 `useRowWindowing` 并列）—— 把
  `@tanstack/vue-virtual` 收口成「传滚动容器 + 行数据 + 行高估值，换回当前该渲染哪些行」。`SongSection`
  超过 50 行时走虚拟化分支，只挂视口附近的行，其余由占位总高顶住；滚动容器由 `SidebarLeft` 经 prop 下发
  （不让 domain 组件跨层 `closest()` 反查宿主的实现细节）。50 行以下仍走原来的全量渲染路径。
- 三处不这么做就会出错的细节，都写进了注释：**① 内核按需 `import()`** —— `@tanstack/virtual-core`
  gzip 约 10.5 KB，而现有产物的首屏闭包已经 216.2 KB / 预算 220 KB（`scripts/check-bundle.mjs`），静态
  引入当场超预算，故与 sortablejs 同一处理：列表真的长到需要虚拟化时才去取那个 chunk；类型导入仍是静态
  的（`import type` 编译期擦除）。**② 虚拟化时一并禁用拖拽排序，并把这件事说出来** —— Sortable 搬的是
  容器里真实存在的子元素，`resolveNextOrder` 遇到「元素数 ≠ 数据条数」会放弃并退回下标运算，算出来的
  顺序与用户所见不符，属于静默改错数据；宁可大列表上不给拖拽，也不给一个会算错的拖拽。禁用之后**必须
  有对应的提示**：另两种「拖不动」都有可见的表达（非手动排序时拖拽本来就没意义，把手直接藏掉；筛选态
  由顶栏那枚筛选徽标显示），只有这一条是「用户以为能拖、却拖不动」而界面上毫无线索 —— 把手不出现、
  拖了也没反应，只能靠猜。故卡片新增 `dragDisabledReason`：有值时拖拽把手以禁用态（`opacity-40` +
  `cursor-not-allowed`）**常驻**，并把「列表较长（N 首），已停用拖拽排序」挂成 tooltip；该状态下
  **不**再补 `pointer-events-none` —— 光标与那条提示都挂在图标自己身上。禁用态取半透明而不是
  `text-fg-disabled`：后者是失效控件的墨色，本仓门禁把它排除在正文三档之外，落在卡片底上亮色只有
  1.68:1，而这里恰恰需要这枚图标**被看见**（用户才会去 hover 它读到原因）；半透明 + 禁用光标是本仓
  表达「看得见但不可用」的既有写法（`BaseDropdownItem` 的 DISABLED_CLASS）。**③ 强制挂载
  当前段落的小标题行** ——
  侧栏滚动条的气泡读数是现查 DOM 的（取「顶沿已越过容器上沿的最后一个 `[data-pinyin-group]`」），拼音
  分组模式下每个字母下常有几十首歌、远超预挂载量，小标题行一旦被挡在窗口外，读数就会跳到下一组。
- 验证：新增文件与两个改过的 SFC 走**最小作用域类型检查**（临时 tsconfig `extends` 项目根配置、只
  `include` 这三个文件 + 全局声明与 `appDbSchema` 合并文件，故 `strict` / `noUncheckedIndexedAccess` /
  `paths` 全部生效）—— 0 错误；`eslint --max-warnings 0` 0 问题、`prettier --check` 通过；
  `vue/compiler-sfc` 离线编译两个 SFC 模板 0 错误、虚拟化分支的绑定全部解析得到（补上 ② 那枚禁用态提示
  后重跑，同样的四道检查再次全绿，并额外核对了渲染函数里 tooltip 确实绑在 `dragDisabledReason` 上、
  两个分支都把该 prop 传给了卡片）；`esbuild` 转译新组合式

### 优化 · 启动不再整屏空白，读侧清洗分片让出主线程（2026-10-04）

- 现象：造出顶满规模（2000 首 × 600 行）的测试数据后，启动要等十几秒，而且这段时间**整个页面没有任何
  内容** —— 工作台与乐谱路由都是。
- 根因：`app.mount('#app')` 写在 `initApp` 的 `finally` 里，前面要 await 完
  `Promise.all([chordStore.hydrate(), songStore.hydrate()])`（或 8 秒超时），而 `index.html` 的 `#app`
  是个空 div —— 挂载前 DOM 上一片空白，路由根本没被渲染过，所以两个路由都一样空。等待本身来自
  `songRepository.loadSongs()`：一次 `idb.getAll('songs')` 把全库乐谱整个读出来，再逐首清洗（重建
  `lineIds`、把 `chordMap` 的普通对象重新物化成嵌套 Map）。实测 100 首 × 600 行是 45.1 MB / 342 ms
  （反序列化 204 + 清洗 99 + 响应式遍历 39），外推到 2000 首约 900 MB、纯 CPU 6~7 秒。
- 修法（三条，都不动挂载时机与数据规模）：**① `index.html` 里加启动占位** —— 直接写在 `#app` 内部，
  随 HTML 首帧就画出来；`app.mount` 在挂载前会执行 `container.textContent = ''`（Vue 3.5.11
  runtime-dom 的 mount 实现），故水合完成的那一刻它自然消失，不需要任何移除代码。挂在容器内部而不是
  旁边正是为了吃到这次自动清理：放旁边就得手写移除，且 `main.ts` 中途抛错会把占位永远盖在应用上。
  样式内联在该文件里（应用 CSS 此刻还没加载），颜色是 `--bg-main` / `--text-muted` 在明暗两套主题下
  的值。**② `loadSongs` 的清洗分片**（`SANITIZE_CHUNK_SIZE = 100`），每片之间让出一次事件循环 ——
  让出用 `setTimeout` 而非微任务，微任务在同一个任务里连续排空、不给浏览器插进来绘制的机会，等于没让。
  **③ 水合兜底超时 8 秒 → 30 秒** —— 8 秒是「整屏空白」与「挂载后先显示空列表」二选一时调的，而顶满
  规模的实测读取在 10~20 秒量级，8 秒会稳定误伤：占位消失、应用带着空列表出现、几秒后数据才补进来，
  看起来像数据丢了。占位已经接住「等待期间显示什么」，这个兜底因此只需接住真挂死（open 永久挂起）。
- 第 ② 条不只是让动画不冻住：不分片时那 2 秒是一个长任务，`main.ts` 那个 8 秒兜底超时的定时器回调排在
  被占满的主线程之后、轮不到执行，「超时即挂载」这条路径形同虚设；分片之后它才真的能兜住。
- 分片不影响清洗语义：`sanitizeSongList` 的重复 id 去重是**跨记录**判重，而 songs 库的 keyPath 就是
  id、`toSongId` 又是恒等转换，跨记录撞 id 不可能发生，故不存在「分片后漏判」的形态。
- 验证：改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过；占位所依赖的「Vue 挂载前
  清空容器（runtime-dom 的 `container.textContent = ''`）、且根组件是 SFC 自带 render 故不会把这段
  HTML 当成模板」已对着 `node_modules` 里 3.5.11 的实现逐行核对。**新增一条单测**：夹具按
  `SANITIZE_CHUNK_SIZE * 2 + 1` 定尺寸（必然跨两次片边界，不写死数字），顺序索引取逆序，断言 201 首
  一首不丢且严格按索引序、未进索引的记录兜底追加尾部 —— 分片失效的形态是静默丢歌，属本仓库最不能出
  的那类错，值得钉住；`vitest run tests/data/repositories.test.ts` 8/8 通过。另做两个探针（用完即删）：
  分片清洗与整批清洗的产物逐字节一致、清洗期间定时器确实被调度。**`pnpm typecheck` / `verify` 未跑**
  （按禁令不代跑），改用最小作用域类型检查（临时 tsconfig `extends` 对应配置、只 `include` 改动文件 +
  全局声明 + `appDbSchema`，故 `strict` / `noUncheckedIndexedAccess` / `paths` 全部生效）：源码侧与

### 优化 · 顶栏构建指示器显示功能谱渲染进度百分比（2026-10-04）

- 现象：乐谱页顶栏那枚构建指示器（spinner）只回答「正在出图」，不回答「到哪了」—— 功能谱一轮渲染要

  活，总页数在排版结束（`pages-planned`）时就定格，分母确定；而排列区的绘制是**按视口分片**的 —— 只有
  挂进 DOM 的行才画，没挂的那几百行这一轮压根不存在，分母随滚动随时在变，算出来的百分比不是任何东西
  的进度。那里保持原样：指示器只回答「正在出图」。
- 进度账是新增的小模块 `src/domains/score/preview/renderProgress.ts`（与同目录的 `scorePreviewCache`
  并列的模块级单例 —— 写侧在预览面板、读侧在 app 层顶栏，走 props / emit 要穿四层），记「已就位页 /
  排版总页数」，在 `pages-planned`（页数定格）与 `onPage`（每出一页）各写一次；是否在跑仍由
  `isPreviewRendering` 回答（那份状态机归 `scorePreviewCache`），账本只记数、不判断状态。
- 读数**读缓存条目、不读屏上页流**：改歌词那条最常见的来路是非流式（内容键换代 ⇒ 屏上那批页不再归
  本轮），期间 `pages` 里挂的还是上一版的整批旧图，照它数会数出一份与本轮无关的读数（往往显示「已
  满」，看着像渲染早完了）；条目才是逐页落账的权威账本，两条来路都写它。已在位的页（同键续跑、按页
  继承）从一开始就计入 —— 它们本轮确实不用再画。
- 读数**宽度自己过渡**：`9% → 10%` 多出一位，宽度不控的话它右侧整组按钮会瞬跳一格（这枚读数不是
  孤立的，它在右组最左端，宽度增长会把整组往右推）。`width: auto` 是没法插值的，所以宽度得由结构
  给出来 —— 数字按「百 / 十 / 个」**逐位成槽**，每位一个 `grid`：空槽列宽 `0fr`、有字符时 `1fr`，
  槽宽就是该字符自己的宽度，位数变化时只有最高位那个槽从 0 展开，列宽天然可插值（实测逐帧线性，
  不是瞬切）。`%` 是紧邻的独立节点、宽度自然，不进这些槽。走 CSS 过渡而非 Vue 的 `<Transition>`：
  变的只是槽的列宽，没有元素进出场；时长/缓动沿用让位那层的 `duration-base` + `ease-standard`。
- **为什么不把数字整体当一个槽、宽度按「位数 × `1ch` + 余量」估**（这是第一版做法，被用户当场否掉）：
  数字的真实步进并不等于 `1ch` —— `font-semibold` 走的是**合成加粗**（这套字体只有 Light / Regular /
  Bold 三档，没有 600），合成把字面撑宽约 0.09ch/位，估算槽宽与内容之间那段差额于是**随位数累积**。
  余量留给哪一侧，哪一侧的边距就随位数漂：第一版把余量放在左边（内容 `justify-end`），数字离 spinner
  的距离便随位数变 —— 用户 2026-10-04 反馈的「percent 的左边边距不一致」正是这一处（实测数字左端
  3.422 / 3.406 / 3.422px，总宽却每档差 8.56px 而数字只差 8.58px）。逐位成槽后不再有估算，数字左端
  与「`%` 跟数字的间距」两侧都恒定，往右长出来的只有 `%` 右侧 —— 这才是「读数变宽了」该有的样子。
- 同一处还修掉过一次裁切：更早的版本把 `%` 也当成一位来估宽，槽比内容窄 2.4px，而 `justify-end` 把
  这一整截全丢在左边 —— 最左边那位数字被啃掉一角（用户反馈「左边的数字被切断了一部分」，实测 `9%` /
  `10%` / `100%` 分别被啃 2.375 / 2.391 / 2.391px）。`%` 比数字宽得多（实测 1.52ch vs 1.00ch），
  它宽度又不随位数变化、压根不需要过渡，拆出去让宽度自然即可。
- 验证：改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过。**`pnpm typecheck` /
  `verify` 未跑**（按禁令不代跑），改用最小作用域类型检查（临时 tsconfig `extends` 项目根配置、只
  `include` 改动文件 + 全局声明 + `appDbSchema` 合并文件，故 `strict` / `noUncheckedIndexedAccess` /
  `paths` 全部生效）：0 错误。另做三个探针（用完即删）：① 用 `vue/compiler-sfc` 的 `parse` +
  `compileTemplate` 离线编译模板，核对 `grid-cols-[0fr]` / `grid-cols-[1fr]` /
  `transition-[grid-template-columns]` / `min-w-0` / `tabular-nums` / `whitespace-nowrap` 都在、`%`
  确实是独立节点、旧的 `scoreBuildPercentWidth` 已清干净；② 用 Playwright（本机已装的 chromium）按
  **真实字体栈与根字号**（`html { font-size: 22.25px }`，故 `text-2xs` 实际是 13.9px）复现读数结构，
  逐档量「数字左端距起点 / `%` 与数字间距 / 总宽」，同时对照第一版做法，坐实了漂移与裁切那两组数字；
  ③ 同一套 Playwright 采样 `0fr → 1fr` 过渡的逐帧宽度（16 个中间帧、线性推进），确认它是插值而非
  瞬切 —— 这一步是方案成立的前提，值得单独钉一次。**未新增单测**：账本只有「记数 / 读百分比」两步，
  `percentOf` 的两个分支在真机上各看一次就够，为它写断言属同义反复；宽度过渡是纯 CSS 表现，断言
  类名属易碎测试。**应用内真机未实测**（探针是等价结构，非真实页面）。

### 优化 · 大乐谱预览拆出更低的超采样档、页脚改叠加层（2026-10-05）

- 现象：150 MB 量级的乐谱（上百页）预览要等约 30 秒才出全图。
- 根因（先探针测量再动手）：单页成本九成以上是 **JPEG 编码**，不是绘制。本机 chromium、质量 0.95
  下逐档实测单页 A4 1588×2246（3.57 Mpx）编码约 **25~37 ms**（其中 3.5 ms 是 `setTransform` 后的整页
  绘制，其余全是 `convertToBlob`）；降到 1.5 约 16 ms、**1.25 约 12 ms**、1.0 约 6 ms —— 编码成本随
  像素**面积**线性缩放。页脚旧做法每页要多一次「整页解码 + 重编码」，约 30 ms/页，比它本要画的那条
  页码贵两个数量级。
- 修法（三条）：
  **① 预览走独立超采样比** `PREVIEW_RENDER_RATIO = 1.25`（导出仍 `SCORE_EXPORT_CONFIG.PIXEL_RATIO`
  = 2.0）。原先全链只有一个常量、导出与预览共用，现改为「一次渲染一份」的模块级状态：`scoreExportLayout`
  新增 `renderRatio` / `setRenderRatio`（与 `applyLayoutScales` 同一时机由渲染消息入口设定），画布构造
  （`acquirePageCanvas` 缺省参）、指板光栅化、恒等贴图对齐、长图反推比（`resolveLongImageRatio`）全改读
  它；导出不传 `renderRatio` 即回落 2.0。取 1.25 而非 1.0：给屏幕放大留半档余量。**指板位图缓存键必须含
  这个比** —— 位图按它光栅化，预览与导出交替渲染同一和弦时若比不入键，会把 2.0 的位图贴进 1.25 的画布，
  指板被放大糊掉。
  **② 页脚缺省关**（`settingsStore.scoreShowFooter` 由 `true` 改 `false`）—— 页码对「先看排版对不对」是
  次要信息，让用户按需打开，而不是默认全民买单。
  **③ 页脚不再「烧进整页」** —— 新增 `footer-band` 请求，产出**页宽 × 页脚带高的透明 PNG 条带**（
  `renderFooterBand` / `renderFooterBands`，只底部有页码像素），实测稳态 **0.6~~0.9 ms / 3~~7 KB 每页**；
  预览模板用绝对定位的第二个 `<img>` 叠加在页图上，开关页脚于是变成**纯 CSS 显隐**（零 Worker 调用、零
  重编码）。两种产物并存：`footer-compose`（自包含整页，导出 PDF / ZIP / 复制本页用）与 `footer-band`
  （预览叠加层）。预览的 `embedFooterPages` 因此恒 `false`。（条带首调可达 48 ms 是编码器一次性初始化，
  测稳态须重复取样。）
- 验证：`vue-tsc --noEmit -p tsconfig.json` 与 `tsc -p tsconfig.worker.json` 均 0 错误；改动文件
  `eslint --max-warnings 0` 0 问题；`vitest run --project ui --project logic` **134 文件 / 1289 测试
  全通过**；`vite build` 通过（含 worker 产物与 PWA 预缓存）。探针（用完即删）用 Playwright 核对了条带
  的透明度（四角 alpha = 0、基线行 17 个墨点）与各档比下的单页编码耗时。**`pnpm typecheck` / `verify`
  未跑**（按禁令不代跑）。**真机未实测** —— 1.25 档在真实屏幕上的锐度观感只能靠眼睛判。
- 已知边界：**等待时间未缩到「快」** —— 1.25 档把编码从约 30 降到约 12 ms/页，上百页仍是数秒量级；
  再往上压只剩「降 JPEG 质量」或「预览改出 WebP」这类会动到画质/兼容性的取舍。

### 调整 · 全局提示（toast）文案精简（2026-10-05）

- 现象：toast 文案普遍偏长 —— 一句话里塞了「动作名 + 失败前缀 + 冗余修饰 + 本该由界面表达的信息」，
  在窄提示条里要折两行才读完；同一条信息重复出现时尤其吵。
- 修法（三类，不动语义、不动控制流）：
  **① 去掉与消息等级重复的前缀** —— `error` 级不必再写「确认失败：」/「保存失败：」，`success` 级不必再
  写「操作成功完成」→「操作成功」。等级本身已由图标与配色表达。
  **② 压掉冗余修饰** —— 「已使用云端数据覆盖本地」→「已用云端数据覆盖本地」、「成功上传至云端」→

  「文件非标准备份或核心数据已损坏」→「文件不是备份，或核心数据已损坏」等。括号里的猜测（「可能…」）
  是给开发者看的，用户不需要。

  一律改直角引号 `「」`。备份与分享相关的「导出时设置的密码」/「分享链接」在上下文已明确时压成「密码」/
  「链接」。
- 验证：改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过；`vue-tsc`（源码 + 测试配置）

  重复出现」的去重合并 —— 那是交互层的另一件事。

### 修复 · 页脚叠加层被拉满整页，页码浮到画面中间（2026-10-05）

- 现象：上一条改动的页脚叠加层上线后，页码显示在**页面中部**，且字形被纵向拉长 —— 页底那行字跑到了
  半页高的位置。
- 根因：条带画布只有 `pageMargin`（A4 为 56 px）那么高，而叠加层 `img` 用的是 `inset-0 h-full w-full`
  —— `inset-0` 把条带**顶端对齐页盒顶端**，`h-full` 又把它从 56 px 拉伸到整页 1123 px。两个后果同时
  发生：条带里那行字的基线（画在条带内 y = 28 处）被等比推到页面中部，字形纵向被拉宽 20.05 倍。
- 修法：改成 `bottom-0 left-0 h-auto w-full` —— 按原始比例贴在页盒底边。条带的**底边**就是页图底边
  （见 `renderFooterBand` 的坐标系注释：条带 y=0 对应整页的 `pageHeight − bandHeight`），故贴底后
  两层逐像素对齐，页码仍落在底部页边距中线上。
- 验证：改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过、`vue-tsc` 0 错误。用 Playwright
  在真实 chromium 里造了一张与 `renderFooterBand` 同构的条带（同坐标系、同基线）再按新样式铺层，
  量测确认：条带高 55.97 ≈ 56、条带底与页底重合、页码基线距页底 27.97 ≈ 28（应落位置）；
  同时量了修前的对照 —— 条带被拉伸到 1123 px、字形纵向拉伸 20.05 倍，正是截图里的样子。
  **`pnpm typecheck` / `verify` 未跑**（按禁令不代跑）；**应用内真机未实测**（探针是等价结构，非真实页面）。

### 优化 · 开发数据「顶满并覆盖」不再整页卡死（2026-10-05）

- 现象：开发面板把规模表单顶满后点「生成并覆盖」，页面整段僵住 —— 不是「有点卡」，是从点击到完成
  期间界面完全不动（确认 loading 的转圈也停着），标签页切不出去。
- 根因（先量后改，两处**都是长任务**，缺一不可）：
  **① 落盘是单个巨型 IDB 事务** —— `songRepository.flushChanges` 把全量 `dirtySongs` 一次性 `put`
  进同一个事务。实测 2000 首量级的单次 `structuredClone` 就要约 **2.0 s**（structured clone 在主线程
  跑），业务里的 `toPlainPersistable` 深克隆叠加事务内克隆，实际更长。
  **② 生成本身是同步 CPU** —— 顶满规模下 `buildDevTestData` 一次跑完不松手，中途没有任何让出点。
- 修法：
  **① 落盘分片**（新增 `FLUSH_CHUNK_SIZE = 200`）：`flushChanges` 改成每 200 首一个事务，**片间
  `yieldToEventLoop`**；`toPlainPersistable` 挪到事务**外**逐片做（它是纯 CPU 深克隆，放进事务回调只会
  把「事务已打开」的窗口拉长到覆盖这段 CPU）。顺序索引改为**独立先落** —— 原先与 dirtySongs 同事务，
  分片后再挂在最后一个片上会让「索引已写、部分歌未写」的窗口变长；索引是派生数据（`loadSongs` 对
  索引缺失/漂移的记录追加尾部，不丢歌），独立成事务不损语义。
  **② 生成分片**（新增 `buildDevTestDataAsync`）：把 `buildSongs` 的循环体抽成 `buildOneSong`，
  同步与分片两条路径共用同一段代码（不复制，防两处漂移），分片版按批调用并在批间让出，共 20 批。
  开发面板改走 async 版。
- **让出是关键，不只是分片**：分片把「一次几秒的长任务」换成多个中任务，但事务排队与提交仍在同一个
  任务里连续发生 —— 不显式让出的话只是把一段长卡顿换成 N 段连续卡顿，观感一样。让出用 `setTimeout`
  而非微任务：微任务在同一个任务里连续排空，不给浏览器插进来绘制的机会。
- **RNG 跨批复用，产出零变化**：种子仍是一个 `createRng(0x5eed0002)`、按 index 升序不跳号取数，
  故分片只改变「什么时候让出」，不改变任何一首歌的内容。
- 验证：新增 `tests/app/devSeedDataEquivalence.test.ts`（4 用例）—— 钉住「分片版与同步版**同构**」：
  规模/估算值/逐首歌由 RNG 决定的产物（歌词、行数、槽位绑定结构、各短字段）完全一致。比较时把
  lineId / chordId 归一成占位符（它们是随机 UUID，两次调用必然不同）而**保留结构位次** —— 绑定关系
  与顺序仍在比较范围内，那才是分片可能打乱的东西；id 与时间戳另立一条只校验形态。
  探针（用完即删）在真实 chromium 里量了让出的效果：12 片 × 180 ms 的同步 CPU，不让出时是一整块
  **2160 ms** 的连续占用（maxGap 180 = 单片时长，浏览器全程插不进来），让出后是 12 个 ~180 ms 的
  独立块（maxGap 与单片持平，片间留出空档）。改动文件 `eslint --max-warnings 0` 0 问题、
  `prettier --check` 通过；`vue-tsc`（源码 + 测试配置）0 错误；`vitest run --project logic --project ui`
  **135 文件 / 1293 测试全通过**。**`pnpm typecheck` / `verify` 未跑**（按禁令不代跑）；**真机未实测**
  —— 顶满规模下的实际观感只能靠眼睛判。
- 已知边界：**没让总量变快**。分片让出会引入少量额外开销（每次让出约一个宏任务），总耗时甚至略增；
  换来的是这期间界面不冻。剩余的两段未动：`replaceAllData` 对和弦库的整批替换、以及顶满规模下
  IDB 本身的写入吞吐 —— 前者量级远小于歌曲，后者受存储层限制。

### 优化 · 启动占位显示真实加载进度（2026-10-05）

- 现象：刷新页面时的「正在加载数据…」只是一个 spinner 加一句静态文案。顶满规模下要等十几秒，期间

- **收在 platform 而不是各加载器直接摸 DOM**：占位既在 Vue 之外、又在数据域链路的下游，而 domain
  不允许反向 import app 层 —— platform 是两边都看得见的唯一合法汇合点，domain 只调一个无依赖的
  纯函数。**必须直接写 DOM**：此刻 Vue 尚未 mount（`app.mount` 在 `finally` 里），没有任何响应式出口。
- **一条总进度，各阶段占固定区间**（`BOOT_PHASES`：准备工作区 0~~15%、和弦库 15~~30%、乐谱库 30~~95%、
  载入界面 95~~100%）。为什么不各段各自 0→100%：各段是**并发**的，实测「和弦库 100%」之后紧接
  「乐谱库 40%」，条儿从右端跳回左端 —— 进度倒退是启动页最刺眼的观感缺陷。改成总进度后条儿
  全程只增不减（`reportBootProgress` 内有一道「不与当前值比小」的守卫兜住并发段的乱序上报）。
  代价说清楚：条宽不再等于**当前阶段自身**的完成度，它回答的是「整段启动还剩多久」；文案里的
  `N / 总数` 才是当前这项的真实读数，两个口径。
- **按比例推进，而不是按字节**：读侧的分母取「库里有多少首」、分子取「已清洗多少首」—— 清洗才是
  这段里真正耗时的部分，用读取字节数做分子会让条儿在清洗阶段停住。
- **没有分片计数的段按时长估算**（`withBootPhase`）：`idb.getAll` 是一次不可分割的调用，拿不到
  「已读多少条」。这些段按预期耗时线性映射到区间内、只走到区间的 90%（末段留给真实读数，
  避免「估算先撞满、真实读数再往回看」）。估算期的**文案不显示数字** —— 它的分母是模块内定的
  模拟量，与真实读数的分母不是一个口径，混着显示会出现「1260 / 10000」紧接「200 / 1200」这种
  无意义且跳变的数字。`estimated` 标记就是为区分这两者而设。
- **必须节流**：读取是「每 100 首一片」的循环，顶满规模要调上百次，每次都写 DOM 会让样式重算挤占
  本就不宽裕的主线程 —— 而这条链路的全部意义就是让主线程喘气。故按「比例推进 ≥ 1% 且距上次 ≥ 60ms」
  才落笔；**阶段名变化立即落笔**，那是用户最需要看到的信息。
- **条带样式修了两处会让人以为「条儿坏了」的写法**：① 轨道底色原先靠 `opacity: 0.22` 压淡，
  而父级 opacity 是**组不透明度**、子元素无法覆盖 —— 填充被一起淡掉，亮色主题下两者都只有 22% 的
  墨，肉眼看着就是一条空轨；改用 `color-mix(in srgb, currentColor 22%, transparent)` 只压淡轨道
  自己。② 不确定态的滑动动画原先是 `translateX(-100%) → 350%`，滑块一个周期里大半时间停在
  轨道外（被 `overflow: hidden` 裁掉），观感同样是一条空轨；改成在 `0 → 150%` 之间
  `alternate` 往复，滑块始终在轨道内。减弱动效下不再让它消失，而是「填满 40% 静置」——
  比一条完全空着的轨道信息量更大。
- 验证：新增 `tests/platform/bootProgress.test.ts`（19 用例，jsdom）—— 覆盖阶段内完成度到总进度的
  映射（含区间端点）、无 phase / 无 total 的退化、越界夹取、**阶段名变化必落笔**（比例仅推进 0.25%
  时也不该被节流吞掉）、小幅推进被节流、**全程只增不减**（并发段报出更小值时条儿不退回去）、
  区间配置错误时最多停在原地、`withBootPhase` 的立刻落笔 / 止步 90% / stop 后不再写 DOM / 占位
  已消失时不留定时器、`BOOT_PHASES` 四区间首尾相接且覆盖 0→1。断言用 `parseFloat` 读百分比 ——
  jsdom 会把 `31.0%` 归一成 `31%`，写字符串断言是脆的。探针（Playwright，用完即删）在真实

→ 78.4 → 85.8 → 93.4 → 103.0 → 115.0 → 121.6 → 134.0`（轨道 180px），**单调递增无回退**，
  文案按 `200 → 400 → … → 1000 / 1200` 推进。改动文件 `eslint --max-warnings 0` 0 问题、
  `prettier --check` 通过。**真机未实测** —— 条儿与文案的实际观感只能靠眼睛判。

  这是正常表现，不是缺陷（它服务的场景本就是「有数据要读」）。

### 优化 · 开发数据「顶满并覆盖」消除一次重复深克隆（2026-10-05）

- 现象：上一条把「整页卡死」改成了「间歇卡顿」，但**总耗时并未下降** —— 让出只是不让界面冻住，
  该干的活一点没少。用户点完仍要等差不多的时间。
- 根因（先探针测量再动手）：落盘链路上**深克隆跑了两遍**。`toPlainPersistable` 是**无条件**的整图
  深克隆，实测 2000 首 × 600 行要 **2684 ms**；而 IDB 收到值之后自己还会 structured clone 一遍
  （实测 **3.1 s**）—— 后一次才是必需的 copy，前一次是纯重复劳动，占了整条落盘链路的三分之一。
- 修法：新增 `toCloneable`（`platform/utils/common`），落盘热路径改用它。它只修「可克隆性」这一件事
  —— **惰性剥代理、全 raw 的子树原引用带过**，落盘分片与 `saveSong` 两处同步改用。
  （本条当时按「顶两层剥代理」实现并记为实测 7 ms —— **那个深度假设是错的**，同批改动里已被证伪并
  重做，见本片段下方「落盘前剥代理漏掉 raw 容器里的代理」一条。）
- **为什么不是裸 `toRaw`**（第一版做法，当场踩坑）：`toRaw` 只剥**顶层**，而 store 里的歌曲常是
  「展开复制」来的 —— `{ ...reactiveSong }` 读的是响应式 getter，复制出来的**嵌套代理**（`chordMap`
  仍是 Proxy）会被 `toRaw` 原样留下 → IDB `structuredClone` 抛 `DataCloneError` → **整批落盘静默失败**
  （表面上看是「改了的标题没保存」）。这也是回归被测试当场抓住的地方。
- **为什么不是完整递归剥代理**：写过一版 `deepToRaw`，正确但实测 **1743 ms** —— 顶满规模下代理图有
  **1580 万节点**，与 `toPlainPersistable` 无实质差别，等于没优化。故改为**惰性下钻**：
  只沿「确实含代理」的路径展开，全 raw 的子树原引用带过，开销随代理的分布而非数据总量增长。
- `toPlainPersistable` 保留但补了注释：**落盘热路径不要用它**，它留给「确实需要一份独立副本」的场景
  （如备份导出）。
- 验证：`overwriteSongs` 端到端 **8114 ms → 4510 ms（-45%）**，其中 2745 ms 正是消除掉的重复深克隆
  （探针实测，顶满规模 2000 首 × 600 行）。新增 `tests/platform/toCloneable.test.ts`。回归侧在
  `tests/data/repositories.test.ts` 补了一条：响应式代理的歌曲经 `saveSong` 与 `flushChanges` 落盘后
  再读回，断言记录确实在库里 —— **把 `.map(toCloneable)` 临时还原成裸切片，该用例当场红**。
  改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过。
  **`pnpm typecheck` / `verify` 未跑**（按禁令不代跑）；**真机未实测**。
- 已知边界：**省下的是重复劳动，不是全部耗时**。改后 4510 ms 里仍有：生成约 3.7 s（分片后仍占大头）、
  IDB 自身那次 structured clone 约 3.1 s、真实读写约 4.3 s（三段有重叠）。再往上压只剩两条路 ——
  降低顶满档的实际数据量，或改走单批写入避开多次事务开销 —— 两者都要动到「顶满」这个入口本身的语义，
  未在本次涉及。

### 修复 · 落盘前剥代理漏掉「raw 容器里的代理」，整批写入静默失败（2026-10-06）

- 现象：上一条改动引入的回归。**改一首乐谱后刷新，改动没了** —— 界面里改得好好的，落盘却什么都没写。
  静默、无报错、无提示，用户唯一能察觉的方式是刷新后数据回退。
- 定位过程：在 `tests/ui` 里撞到两条既有的跨歌隔离用例失败（`expected undefined to be 'c1'`），
  顺着查到 IDB 里**一条记录都没有**。把 `flushChanges` 的 `toCloneable` 临时换回
  `toPlainPersistable` 后当场转绿 —— 确认是上一条改动的回归，不是既有噪声。
- 根因：**Vue 的深层响应式是「读时按需包代理」，raw 容器不会把元素也变 raw**。
  `toRaw(map)` 只让 Map 自己变 raw，里面装的 reactive 槽位对象**一个都不会跟着变**。
  上一条的实现写着「容器不是代理 ⇒ 原样带过」，于是 `chordMap` 这种「Map 套槽位对象」的结构把一整片
  代理原封不动交给 IDB → `DataCloneError` → 被 `flushOnce` 的 catch 吞成「下次重试」→ 静默不落盘。
  逐层探针实测的真实形态：
  ```
  song.chordMap              Map    proxy=false   ← 容器本身是 raw
  song.chordMap.get(lineId)  Object proxy=true    ← 元素是代理
  song.chordMap.get(...).char  Map   proxy=true    ← 代理的字段也是代理
  ```
  这条同时证伪了上一条记录里的「代理只存在于最上 1~2 层、故有界浅层足够」——
  **深度假设是错的**，代理可以藏在任意深度的容器元素里。
- 修法：`toCloneable` 改为**惰性递归**（`stripProxies` + `stripContainer`）——
  ① **容器一律下钻**（不再看它自己是不是代理）；
  ② **普通对象也逐字段下钻**（`{ ...reactiveMeta }` 这类展开复制产出的是普通对象、字段却是代理，
  只看本层同样会漏）；③ 靠**引用比对**决定要不要重建本层：子结构全 raw 时原引用返回、一次分配都不做。
  另加 `MAX_STRIP_DEPTH = 12` 作**「环」的保险丝** —— 撞上限时剥掉该层即停，环必然终止；
  留下的深层代理会让 IDB 抛 `DataCloneError`（可见失败），不会像无上限递归那样把主线程挂死。
- 成本复核（顶满规模 2000 首 × 600 行，探针实测）：全 raw **34 ms**、整块响应式 **29 ms**、
  `toPlainPersistable` 对照 **680 ms** —— 惰性下钻没有退化成深拷贝，上一条省下的量级保住了。
- 验证：`tests/ui/songStoreCrossSong.test.ts`（2 用例，改前红、改后绿）钉住端到端；
  `tests/platform/toCloneable.test.ts` 扩到 12 用例，新增两条**形态用例**——
  「raw 容器里装着代理」与「普通对象的字段是代理」，两条都先断言输入确实 `structuredClone` 抛错
  （否则会退化成恒真），再断言产物可克隆且**内容不丢**（键、槽位、槽位里的字符逐项比对）；
  另新增「全 raw 的嵌套结构整体原引用返回」（钉住惰性，防以后有人改成无条件重建）与
  「成环结构不会挂死」。`vitest run tests/ui tests/data tests/stores tests/app tests/platform`
  **86 文件 / 528 测试全通过**；改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过。
  **`pnpm typecheck` / `verify` 未跑**（按禁令不代跑）；**真机未实测**。
- 已知边界：`MAX_STRIP_DEPTH` 只防环，不是「只剥到第 12 层」的语义承诺 —— 正常实体的代理分布只有
  三四层，撞上限说明数据结构异常，那时宁可让 IDB 报错也不要继续下钻。

### 修复 · 委托式右键菜单在非触发区右键不关闭（2026-10-06）

- 现象：列表级单例菜单（右键由容器事件委托驱动）打开后，右键列表里**没有触发语义的区域**
  （行间空白、列表底部留白、页面之间的间距）菜单**既不关闭也不换位**，就那么卡在屏幕上不动。
- 根因：`BasePopover` 对右键的「是否在区域内」判据是 `contextTriggerEl.contains(target)`，
  而委托式用法报的 `contextTriggerEl` 是**整片列表容器**（只有它才有真实尺寸，内部那个只包默认插槽的
  包裹层是 `display: contents`、恒为零矩形）。空白处同样落在容器里 → 判为「内部」→ 不关闭；
  而委托的 handler 反查不到目标（没有 `data-song-id` 之类的标记）→ 也不打开。

- 修法：新增 `contextTriggerSelector`（`BasePopover` / `BaseMenu`），让调用方声明「容器里哪些后代才算

  「容器本身就是触发器」那类用法（`BaseInput` 搜索面板）不变。四处委托消费方同步报上选择器：
  乐谱列表 `[data-song-id]`、和弦卡片 `[data-chord-id]`、分组头 `[data-collapse-head]`、

- 选择器与委托 handler 的 `closest()` 反查**必须同源**，故和弦库那两个抽成了导出的常量

  一半上生效的错。左键那条 `keepOnContextTriggerClick` 豁免一并改走同一判定：委托用法下
  「点在容器里」不等于「点在触发器上」，点在空白处时关掉菜单才是对的。
- 验证：新增 `tests/ui/menuDelegatedContextClose.test.ts`（5 用例）—— 空白处右键**必须关闭**、

### 修复 · 乐谱卡的拖拽把手夺焦并触发 aria-hidden 违规（2026-10-06）

- 现象：控制台报 Chrome 无障碍违规 —— 「Blocked aria-hidden on an element because its descendant
  retained focus」，被聚焦的元素正是乐谱卡行尾那枚**禁用态拖拽把手**（`aria-hidden="true"` 的
  `BaseIcon`）。点卡片时焦点会落到这枚 14px 的装饰图标上，而不是卡片本身。
- 根因（在真实页面里逐步定位）：**Chrome 把 `<svg>` 当成可聚焦元素**，而该图标的图标路径是
  `fill:none` 的描边 —— 点击的命中目标就是 `<svg>` 自己，于是浏览器把
  `document.activeElement` 直接落到这个 `aria-hidden` 的 svg 上。实测排除了两条常见误解：
  `tabindex="-1"` 与 `focusable="false"` **都拦不住**（Chrome 对 svg 不认这两个），
  加 `pointer-events: none` 才有效（命中目标变成父元素，浏览器转而聚焦最近的可聚焦祖先＝卡片）。
  又用「把该 svg 连同全部属性克隆到 body」做了对照 —— 克隆不可聚焦、原节点可聚焦，
  确认问题出在「它是活的命中目标」而非属性本身。
- 修法：图标外面包一层 `span`，把 `v-tooltip` 与 `dragHandleClass`（cursor / opacity）挪到这层上，
  图标自己恒 `pointer-events-none`。span 与图标同尺寸，tooltip 的锚点几何不变；
  cursor 与 tooltip 本来就只需要一个**可命中的载体**，而这个载体不必是那枚 aria-hidden 的图标。
- 验证：探针（Playwright，用完即删）在真实 dev 环境里对照修复前后 —— 修复前「点卡片」有 1 条、
  「Tab 25 次」有 12 条焦点落在 aria-hidden 子树内；修复后**两处都是 0 条**，`activeElement`
  稳定为卡片本身。同时核对了行为没有丢：包裹层拿到 `cursor: not-allowed`、`opacity: 0.4`，
  图标中心点的命中元素变成包裹层，悬停仍能弹出 tooltip（实测文案「列表较长已停用排序」）。
  `vitest run tests/ui tests/platform tests/data tests/stores tests/app` **86 文件 / 528 测试全通过**；
  改动文件 `eslint --max-warnings 0` 0 问题、`prettier --check` 通过、SFC 模板离线编译 0 错误。
  **真机未实测**。
- 已知边界：只改了乐谱卡这一处。**同一形态（装饰性 `aria-hidden` 图标 + 自带 tooltip 且可被点中）
  在别处可能同样夺焦** —— 但那些图标多包在按钮里（命中目标是按钮、不是 svg），未逐个核对，
  本次不扩大范围。若再现同类违规，按本条的办法处理：把 tooltip 与 cursor 挪到一层非 svg 的载体上。

  （`ø` 先命中、`7` 成残留），这类坑只能靠注释与「记得长的写前面」维持；② **大小写要另开一档** ——

### 修复 · 和弦抽屉保存后回到选择器列表整段空白（2026-11-09）

- 现象（用户上报）：在和弦选择面板里打开「新建 / 编辑和弦」抽屉，保存成功、抽屉收起后，回到面板
  看到的是一大片空白 —— 只有零星的卡片还在，其余位置连「暂无和弦」的空状态都不显示，滚动一下才自愈。
- 根因：**行窗口在「面板被隐藏」的那一帧被算歪，且恢复显示没有第二次机会**。
  和弦抽屉是从面板里打开的，而 `BaseFloatingPanel` 的「模态让位」会把整个面板 `display:none`
  （理由见该组件：面板走 top-layer、恒压在模态之上）。保存会新增和弦 ⇒ `chordSections` 变化 ⇒
  `usePickerVirtualList` 的 watch 在下一次 tick 跑 `updateWindow()`，**那一刻几何全是零矩形、
  `scrollTop` 也恒读成 0**：算出来的窗口退化成「每个分区只剩头一两行」，`observedScrollTop` 基线
  同时被污染成 0。而面板恢复显示的这一次 `display` 翻转**不派发 scroll**、面板自己的 `visible`
  也从头到尾没变（那条 watch 不会重跑），于是这个残缺窗口就一直留着 —— 用户此刻若停在中部或
  尾部的分区，视口里恰好一行都没挂载，看到的就是整段空白。
- 修法（`usePickerVirtualList`，两处配套）：
  **① 隐藏态不计算窗口** —— `updateWindow` 前先判「容器量到过排版高度、现在却为 0」，
  命中即直接返回，保留上一次有效窗口（也不碰 `scrollTop` 基线）。判据带 `everLaidOut`：
  jsdom 里 `clientHeight` 恒为 0，若把「从未量到」也算隐藏，任何挂载本面板的用例都会拿到空窗口。
  **② 恢复显示补算一次** —— 对滚动容器挂尺寸观察，只在「高度 0 → 非 0」这个翻转方向上跑
  `refresh() + updateWindow()`（隐藏方向什么都不做：那时读的是零矩形，算高亮只会写成空）。
  与「面板由关到开」`wakeVirtualList`、「列数变化」两条既有补算同源，都是「几何变了必须重算窗口」。

### 修复 · 移动端保存操作栏的三枚钮文字越出胶囊（2026-11-09）

- 现象（用户上报）：手机首页（工作台）编辑和弦时，贴底的保存操作栏文字**越出胶囊圆角之外**，

- 根因：栏内是**三枚文字钮并排**（放弃修改 / 作为新和弦保存 / 更新保存，编辑态才有第三枚）。

  三枚钮 + 两条分隔线在 390 视口下约 445px，而上限只有 345.5px（320 视口下 275.5px）；

- 修法（`WorkbenchView`，只在手机档 `< md` 生效，桌面档一字未动）：
