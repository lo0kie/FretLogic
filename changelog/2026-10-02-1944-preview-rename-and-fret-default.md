### 修复 · v-stagger 用例的收口等待预算不足（2026-10-02）

- 现象：`vStagger` 里两条断言「动画收口后内联值被清掉」的用例偶发失败，报
  `expected '1' to be ''` —— 看着像清理没生效。
- 根因：收口时机不由配置里的 `duration` 决定 —— `ease` 是 spring 时 anime.js 用
  `ease.settlingDuration` **覆盖** `duration`，而它是按 stiffness / damping 解算出来的：当前参数
  （240 / 22）约 0.9s，再叠上 `stagger(40)` 给第二项的延迟，收口落在 ~0.95s。`vi.waitFor` 的默认
  预算恰好是 1s，只差 5% —— 单跑能过，全量并发 / CI（多文件抢 CPU，rAF 与轮询定时器一起被拖慢）必翻。
- 修法：抽出 `waitForSettle`，显式放宽到 10s。用例断言的是「收口后内联值被清掉」，不是「收口发生
  在 1s 内」；放宽只影响失败时多等一会儿，不影响通过时的耗时。
- **为什么是 10s 而不是「刚好够」**：上面那个 0.95s 是**单跑**的数字，全量下余量要按**倍数**留 ——
  CI 的 runner 只有 2 核、132 个测试文件抢 CPU，rAF 与 `vi.waitFor` 的轮询定时器一起被拖慢，两次
  失败都出在「预算只比结算时长高一点」这一档（1s 对 0.95s，只差 5%）。上限由全局 `testTimeout`
  （`vite.config.ts` 里的 15s）兜住：超时值必须留在它之内，否则用例先被 vitest 判超时，报出来的错
  与「清理没生效」完全是两回事。

### 变更 · 工作台保存：没有目标分组时改为弹出分组选择（2026-10-03）

- 需求：工作台新建和弦时若还没选分组，此前点保存只得到一条「保存失败：请先选择目标分组」的提示
  （外加按钮抖一下），缺的那一步要用户自己去找。改为**直接弹出分组选择框**，选完即存。
- **明确不采用「把保存按钮禁用掉」这条做法**：分组是这次保存唯一还没交代的东西，而按钮本身没有任何
  「还缺什么」的线索 —— 禁用只会让用户对着一个点不动的按钮猜原因；弹窗把缺的那一步摆出来即可。
  保存按钮的禁用判据（缺和弦名 / 指板为空，见 `useChordDraftSaveState`）因此**一个字节都没动**。
- 触发条件按「有没有目标分组」判，而不是按「是不是新建态」：目标分组**就是侧栏当前选中的分组**
  （`chordStore.selectedGroupId`）—— 与 `chordDraftValidation` 对新草稿的取值口径**同源**（那边取
  `ctx.selectedGroupId`）。于是侧栏已选中分组时保存照旧一步到位，只有它为空时才弹窗 —— 与抽屉那条
  「新建态一律弹窗」的流程**有意不同**：抽屉是一次专注的新建，工作台的侧栏分组多数时候已经就位，
  每次都弹反而多一步。
- **判据刻意不看草稿自己的 `groupId`**（初版写的是 `draft.groupId || selectedGroupId`，这就是本次那个
  坑）：校验对新草稿只认 `ctx.selectedGroupId`、从不读草稿的 groupId，于是那个多出来的来源一旦生效，
  判据就会以为分组已就位而**跳过弹窗**，紧接着在校验里撞上 `NO_SELECTED_GROUP` —— 用户看到的是
  「弹窗被跳过、却仍被告知请先选择目标分组」。判据与校验同源之后，这种错位在结构上不可能发生。
- 确认分组 = **先落 store、保存成功才算选定**：把所选分组写进 `selectedGroupId`（校验的目标分组取自
  这里）→ 保存 → 成功才关弹窗；**失败要把这次选择撤回**（还原成进弹窗前的选中，而走到这一步时它必为空，
  故等于取消选中）。撤回是必需的：失败时弹窗刻意不关、分组也仍高亮着（供原地重试），可一旦用户手动
  关掉弹窗，那个分组就成了一份没人认领的残留 —— 下一次保存会以为分组已就位而跳过弹窗、再给一条
  「请先选择目标分组」（他明明刚在弹窗里选过），「再点一次保存」于是成了一条死路。
- 另两档也不弹：编辑态的分组沿用和弦自己的（校验里回查原实体，此时用户取消选中分组也不该拦 ——
  `chordDraftValidation` 里那条「纯更新优先沿用原实体分组」说的就是这件事）；一个分组都没有时弹窗里
  也没得选，仍交给校验提示「请先新建分组」。
- 弹窗复用抽屉那套 `GroupPickerGrid`（交互、外观与列数档位因此天然一致），但**不传**
  `active-group-id` / `active-tooltip`（抽屉传了）：本视图里「当前所属分组」这个概念不存在 —— 走到
  这一步时目标分组必为空，网格一开就不该有任何一项带高亮；草稿自己那个 groupId 是「另存为新和弦」
  留下的原分组、并不参与这次保存的目标，拿它当 active 只会让「和弦当前将保存到此分组」说反。
- 打开弹窗时把选中清成当前目标（必为空）：用户在上一次弹窗里点过分组、又手动把弹窗关掉时，
  `selectedTargetGroupId` 会留在那个分组上，不清就会让网格一开就带高亮、确认钮一开就可点（什么都没选
  却能直接确认）。
- 弹窗 Teleport 到 body，不随本视图的 DOM 一起被 KeepAlive 摘掉，故补一条 `onDeactivated` 收起它，
  否则切走页面后遮罩会独立残留在页面上。

### 修复 · 文本协议：BOM 与三处未转义的内嵌值（2026-10-03）

- **`normalizeLines` 不剥 UTF-8 BOM**：Windows 记事本 / Excel 另存为 UTF-8 会写入不可见的 U+FEFF，

- **单和弦 `NAME:` 未转义**：`chordTextCodec` 里那段注释本就点名「`NAME:` 必须转义」，但只有分组名

  `STRINGS:` 等字段行。读写两侧按同一口径补上 `escapeFieldValue` / `unescapeFieldValue`。
- **`TS:` / `PLAYKEY:` / `CAPO:` 裸拼**：类型上是枚举与数字，但值可经备份导入 / 云同步绕过 UI 落到

  只需保证「不拆行」，剥掉换行即可（不改条件写入：那会让「缺行」与「值非法」在往返后不可区分）。

### 修复 · 指板音符滑行「落位前突然变慢」（2026-10-03）

- 现象（用户描述）：滑动指板音符时，落位前几帧**就像是突然变慢了**。
- 根因：补间时长是**定值** 180ms，与走多远无关，于是拖拽段与落位段的**速度**天差地别。
  拖拽时每一帧都在重定向，而每次重定向都从当前帧重放曲线 —— 音符只吃到缓动最陡的起步段
  （`--bezier-sidebar` = `cubic-bezier(0.2, 0.8, 0.2, 1)`，起步斜率 4），每帧走掉剩余距离的一大半；
  一旦松手、不再重定向，那一次补间要跑完整条曲线，速度回落到平均 1×。两段之间就是一次几倍的
  速度骤降，读起来正是「落位前突然变慢」。
- 修法：**打断在途补间的那种重定向，时长按距离缩短**（下限 60ms）；全新的一次（换和弦，上一段已
  播完）仍取满时长，观感与改动前一致。缩短后 `位移 / 时长` 在每一轮里都是同一个比值
  （`基准 / 满时长`），两段的每帧推进量相同，速度连续，落位读起来是自然的减速而不是骤降。
  基准取「本宿主上出现过的最大位移」（只增不减）——它与调用方给的满时长天然对齐，又不必让指令
  import 任何几何模型（指令不知道品距，也不该知道）。
- 附带把「尾段爬行」这个猜想排除掉了：按参数方程算，该曲线 **u=0.8 时 t=0.608、进度 y=0.973**，
  即 97.3% 的距离在前 60%（约 110ms）走完，剩下的 2.7% 摊在最后 70ms —— 一个 25px 的位移尾段
  只挪 0.68px，肉眼不可见。所以问题不在缓动形状，而在两段速度不一致。
- 验证：`tests/domain` + `tests/composables` 28 文件 **614/614**；改动文件 `eslint --max-warnings 0`

  （本项目 typecheck 无文件级形态，按禁令不代跑）；**真机未实测** —— 观感只能靠眼睛判。

### 修复 · 指板音符滑行：拖拽中的重定向不再参与错峰（2026-10-03）

- 上一条（时长按距离缩短）之后用户复测仍「突然变慢」，本次补上同一处代码里的第二条成因。
- 错峰（`delay = 名次 × 18ms`）是给**一次离散变化**用的读法：让人看清哪几根弦动了、动了多远
  （见指令文件头第 ① 条）。而拖拽是**连续跟手** —— 每一帧都重定目标，每一次都按当帧的剩余位移
  重排名次，而剩余位移又随上一帧的推进量变化，名次于是逐帧抖动：同一根弦这一帧排第 0（立即起手）、
  下一帧可能排到第 5（等 90ms）。单根弦的位移因此变成「走一大步 → 停几帧 → 再走一大步」的顿挫。
  落位那一下最明显：剩余位移最小的那根弦名次最靠后，眼看别的弦都停了，它还要先等一格错峰才开始动。
- 修法：`stagger = !uniform && !retarget` —— 重定向（上一段补间还没播完就重定目标）一律 `delay: 0`。
  离散变化（换和弦，上一段已播完）的错峰行为**完全不变**。

### 修复 · 指板音符滑行：拖拽跟手改走 linear，离散变化仍走令牌曲线（探针实测，2026-10-03）

- 用户第三次复测仍「滑动整排整排切换时卡顿」。按用户要求改用探针实测（`tests/browser` 的真实 Chromium，
  逐帧采样 `<g>` 的 `translateY`），先量出两件事：
  1. **先前那条「曲线从未生效」的判断是错的**，已撤回：当时量到「挂载后的 `<g>` 读不到继承令牌」，
     是 **Vitest `mount` 环境的产物**，不是浏览器行为 —— 同一份对照里用 `createElementNS` 手工搭出的
     `<svg><g>`（含套一层容器 div）**读得到**令牌。线上 `readGlideEase` 一直是好的，曲线一直在生效。
  2. **真正的成因是曲线的形状与「逐品跳变」这个目标形态不合**：目标是逐格跳变的，而减速曲线每次重起
     都把距离的一大半压进第一帧（实测单格 25px 有 **54%** 落在首帧），随后尾段几乎不动；下一个品位的
     跳变到来时又从「几乎不动」骤然回到「一大跳」。逐帧位移于是成为
     `13.6 → 5.2 → 2.6 → 1.5 → 0.9 → 0.5 → 0.35 → 6.8 → 7.8` 的**锯齿**，**峰谷比 22×** ——
     观感正是「整排整排切换时一顿一顿」。
- 五条候选曲线的同一场景实测（峰谷比 = 稳态段最大/最小每帧位移）：
  `sidebar 22×`、`roll 14×`、`out 5.8×`、`standard 3.9×`、**`linear 1.7×`** —— 只有线性不产生脉冲。
- 修法：**曲线分两档，判据是「这次是不是在跟手」** ——
  - 离散变化（换和弦，上一段补间已播完）仍走令牌曲线 `--bezier-sidebar`：首帧吃掉 56%、随后单调减速，
    这是设计要的「即刻起步 + 单调减速」，换和弦的观感一个字节没动；
  - 拖拽中的重定向（上一段还没播完）走 `linear`：稳态每帧推进量恒定（实测 2.1~3.4，峰谷比 **2.0×**），
    音符与手指同速跟手，锯齿消失。
    「在途补间是否还在跑」这个判据自带一个正确性质：手指在品位间停超过一次滑行时长时，每一步都是一次
    独立的离散变化，本就该减速落位，而那时**不会**出现锯齿（下一跳在上一跳收尾之后才来）。
- 顺带把令牌的读取改到 `:root`（令牌的唯一定义处，与宿主是否在文档树里无关）并缓存编译结果 ——
  `compileEasing` 每次都新建一个贝塞尔求值函数，而这条读法换和弦时每次都要跑。
- 新增 `tests/browser/noteGlideEase.test.ts`（真实 Chromium，2 用例）：钉住「离散变化首帧显著大于平均、
  前 1/3 帧吃掉六成以上、前半段位移多于后半段」与「拖拽稳态峰谷比 < 2.5、且没有一帧吃掉单格的
  1/4」。把拖拽那一档换回令牌曲线，第二条当场红 —— 这个缺陷此前零覆盖。
- **采样改用 MutationObserver 盯内联 `style`**（指令每帧写一次 `transform`），不再用 rAF 轮询：
  轮询与动画自己的 rAF 落在同一帧上而顺序不保证，某帧会读到「还没更新」的位置（位移 0、被过滤
  滤掉），下一帧就把**两帧的量**记在一起 —— CI 上正是这样报出「前帧 4.19、后帧 6.41」的假反弹
  （位置本身单调，抖的是区间宽度）。形状判据随之改为**相对量**（与平均值比、与 1/3 帧比），不写死
  某次探针读到的百分比：「首帧吃掉 56%」那类数字换一套采样或换一次帧率就会落到 40%，拿它当阈值
