### 修复 · shift_frets 下移调把落到绝对 0 品的弦静音（2026-10-01）

- 现象：`shift_frets` 模式按半音数整体平移品位时，降调落到 0 品的弦被一律静音 —— 和弦名已经降了，
  指法却缺了这个音。
- 根因：判据写成 `shifted > 0`，把 `shifted === 0` 一并当成越界。而 `fret 0` 在这个模型里是
  **绝对 0 品（空弦）**：`pitch.calcNoteMidi` 只在 `fretVal > 0 && fretOffset > 0` 时叠加把位偏移，
  故 `fret 0` 的音高就是调弦音、与 `fretOffset` 无关。窗口从 0 品起步时，「原 N 品降 N 个半音」的
  目标音高恰好就是空弦音 —— 写成 0 才对，静音是错的。
- 修法：`shifted === 0` 且 `chord.fretOffset === 0` 时保留为 0；窗口不从 0 品起步时目标绝对品位是
  `fretOffset ≠ 0`，而 `fret 0` 表达不了它（恒为空弦），仍按越界静音。横按侧不变（0 品横按本就无意义）。
- 同步订正原用例的注释：它把「按着的品降到弦枕」与「本来就是空弦」混为一谈，判据与理由都只在
  `fretOffset > 0` 时成立，而该用例自身是 `fretOffset: 0`。
- 验证：`tests/domain/transposition.test.ts` 9/9（原用例改为断言保留 0，另加一条 `fretOffset: 3`
  的对照用例锁「仍静音」）；`pnpm eslint` 0 问题。

### 修复 · 移调后后缀首字符被根音吃掉（Db#5 降 13 个半音 → C#5）（2026-10-01）

- 现象（测试里以 `it.todo` 登记的已知缺陷）：后缀以变音记号起头时（`#5` / `b9` / `#11`），移调
  改变根音拼写会让这个记号被重新切给根音 —— `Db#5` 位移 -13 拼出 `C#5`，而 `C#5` 被读成
  「`C#` 强力和弦」，音集从 `{0,4,8}` 变成 `{0,7}`。
- 根因：`nameToSegments` 的根音正则 `/^([A-G][#b♯♭]?)/i` 只吃**一个**变音记号，而渲染侧是裸拼接。
  根音自带变音记号时无歧义（`Db` + `#5` = `Db#5`）；根音不带时（`C` + `#5`）与「`C#` + `5`」在
  词法上完全同形 —— 字符串层面无法区分，只能加一层显式隔离。
- 修法（渲染 + 解析两端各一处，缺一不闭合）：
  - 新增 `chordName.isolateQualityFromRoot(rootStr, quality)`：后缀以变音记号起头、根音不带变音记号
    时给后缀套一层括号（`C(#5)`），根音正则遇到 `(` 即止，切分点唯一。`segmentsToString`（覆盖
    `getChordName` 全路径）与 `transpose.transposeChordName` 共用它。
  - `nameToSegments` 新增 `stripWrappingParens`：后缀位置的外层括号没有乐理语义，剥掉后按 `#5`
    解析，与 `Db#5` 的结果一致。只在「原样识别不出」时才剥，故 `(no3)` / `(b5)` 这类**括号本身即
    token 拼写**的写法仍走原路径。
- 验证：`tests/domain/chordTheoryProperties.test.ts` 14/14（`it.todo` 换成真用例：断言 `Db#5 -13`
  得 `C(#5)`，且重解析后除根音外分片与原型逐字相同；另加一条「根音自带变音记号时不做隔离」）；
  chord 域 12 个文件 408/408 通过；`pnpm eslint`（5 个改动文件）0 问题。

### 修复 · 预览缓存的全洞空壳条目导致无休止重渲（2026-10-01）

  - `scorePreviewCache.ensureEntry` 对同键条目**无条件**原样返回，空壳那条的 `total` /
    `pageLineRanges` / 行指纹都是**上一轮**排版的读数；本轮按新页数逐页写入后

    「按页继承」一并挡掉 —— 它手里没有可跳过的页，谈不上「同键续跑独占本轮」。
- 修法：
  - `ensureEntry` 的契约收窄为「**手里还有页**在位的同键条目原样返回」；全洞空壳按本次排版
    **就地重置**元数据。刻意就地改写而非换新对象：屏上与调用方手里都握着这个条目的引用，换新对象
    会让它们指向一条已被 `onEvict` 摘掉的死物、此后写入被 `isWritable` 逐页拒掉；而空壳**没有任何
    页 URL 可丢**（洞不是产物，页脚合成层只对在位页生成），重置不损失任何资源。
  - `ScorePreviewPane` 新增 `resumable`（= 缓存命中 **且** 至少一页在位）作为「本轮能接着用的同键
    条目」，`adoptCachedRender` / 判废守卫 / `havePages` / 继承闸门四处统一改判它；空壳不再挡继承，
    改由 `ensureEntry` 按本次排版接管。
- 验证：`tests/ui/scorePreviewCache.test.ts` 18/18（新增 2 条：空壳按本次排版重置后 `isComplete`

### 修复 · 渲染线程的未捕获错误被误算到当前任务并终止线程（2026-10-01）

- 现象：上一笔请求遗留的异步工作（被中断的那一笔里某个 promise 事后才落定并抛错）会触发 Worker 对象的
  `error` 事件；该事件**不携带任何请求标识**，主线程只能把它算在此刻在跑的那一笔头上 —— 当前任务被误判
  失败，整条渲染线程还被 `terminate()`（指板位图缓存与已装载的字体子集一起丢，下次渲染重新下 1MB）。
- 根因：worker 入口 `self.onmessage` 的整个异步体已被 try/catch 包住，属于当前请求的失败一律走带请求
  上下文的 `postError` 信封；因此能冒到全局的错误**必然不属于**当前请求，而主线程的 `worker.onerror`
  无从知道这一点。
- 修法：把运行时错误的归属收敛到线程自己 —— worker 入口顶层新增 `error` / `unhandledrejection` 兜底，
  `preventDefault()` 阻止其继续上报给 Worker 对象，只留一条控制台记录。主线程那条 `onerror` 因此只剩
  「线程根本没起来」（模块加载失败 / 语法错误，那时兜底还没装上）这一种情形，原有的 terminate + reject
  正对这种情况。
- 验证：`tests/services/workerExportService.test.ts` 4/4；`pnpm eslint` 0 问题；prettier 通过。
  worker 的全局兜底无法在 jsdom 里起真实线程，该路径无自动化用例，改动依据是上面的错误归属推理。
