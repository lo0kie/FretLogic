## 📁 一、临时文件与工作文档约束（Temp File Policy）

1. **严禁主动创建工作文档**：
   - 不得未经用户要求主动创建任何总结/记录类文档（如 `*.md`、TODO 清单、变更日志、分析报告等）。
   - 仅当用户**明确要求**保存或输出文档时才允许写文件；默认一律以回复文本形式呈现。
2. **临时文件必须收敛到 `.temp/`**：
   - 排查/验证/实验用的临时产物（探针 HTML、临时脚本、中间快照、日志等）一律写入 `.temp/`
     目录，严禁散落在根目录或 src 内。
   - 该目录已被 `.gitignore` 忽略；任务结束后如确认不再需要，应主动清理。
   - 唯一例外是按被测机制要求必须落在别处的探针（例如验证 `.codebuddy/rules/`
     注入时，探针**必须**放在该目录内才可能被扫描到）。这类例外须在回复中说明理由，并在测试结束后立即删除。
3. **严禁创建工作区记忆文档**：
   - 严禁在 `<项目>/.workbuddy/` 下创建任何文件，尤其是 `memory/YYYY-MM-DD.md`、`memory/MEMORY.md`
     这类「工作区记忆」文档。
   - 本项目根的 `.workbuddy` 已被**有意**占位成一个普通文件：对该路径的任何写入都会以 `ENOTDIR`
     失败。撞到这个错误时**不要绕过**——不要换文件名、不要换父路径、不要换写入工具、不要改走 shell 重定向。它就是预期行为，如实上报即可。
   - 同理，用户级 `~/.workbuddy/MEMORY.md` 也不在授权范围内，除非用户当轮明确要求。
   - 本条的成因与边界见项目根 `.workbuddy` 文件自身的说明。
4. **严禁用展示类工具把文件推到侧边栏 / 结果区**：
   - 严禁主动调用 `present_files` —— 或任何会打开预览面板、结果区、产物卡片的等价工具。交付一律以**回复文本**
     形式呈现；用户要看文件时自己会打开。
   - 这是硬约束：不因为「流程惯例上要展示产物」「本轮产出了可查看的结果」「宿主提示要求展示」而破例。只有用户**当轮明确说**「打开 / 展示这个文件」才可例外。
   - 附带一条：`show_widget`
     只在对话内联渲染、不开侧栏，不受本条约束；但仍受第 1 条「未经要求不主动产出文档」的精神约束，不要为了凑视觉而用它。

## ⏱️ 二、小任务纪律（Small Task Discipline）

小需求必须小步交付，严禁把简单任务膨胀成全链路大扫描：

1. **先估规模再动手**：接到需求先判断规模（如「更新一个 JSON 样例文件」）。凡可通过「读 1~2 个文件 + 局部修改」完成的任务，直接执行，严禁为此启动全项目扫描、通读校验管线、逐层调试源码。
2. **最小探索原则**：只读完成当前任务直接相关的文件。需要确认字段格式时，优先看实体类型定义（types.ts）或现有同构文件，**不需要**为了一个样例去验证整个校验/导入/导出管线的运行时行为。
3. **验证成本与任务规模匹配**：具体分级标准见 `03-scoped-verification.md`
   的「1.1 验证范围分级」，小任务只需按对应级别做一次简单校验，严禁编写多层调试脚本、临时打点、往返验证链——除非首次交付被用户指出确有问题。
4. **交付优先，迭代兜底**：小任务宁可先给出 90 分结果让用户验收，也不追求一次性证明所有边界。发现问题再按 Bug 修复流程单独排查。
