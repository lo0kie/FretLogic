## 🧪 一、防垃圾测试与测试质量红线（Anti-Tautology & Test Quality Discipline）

严禁为了凑测试数量或覆盖率编写没有实际质量收益的“1=1 自嗨测试”与“脆弱型易碎测试”：

1. **绝对禁写“1=1”同义反复测试（No Tautological Tests）**：
   - **严禁测试框架内置行为**：例如挂载组件断言 `props.label === 'foo'` 时文本是否为
     `'foo'`（这是 Vue 框架的功能，不是业务逻辑）；
   - **严禁测试纯访问器与空包装**：例如单独为 `x => x.id` 这类没有任何分支的 getter 写单测；
   - **严禁测试原子 UI 的 CSS 类名与内联样式**：严禁断言 `expect(el.classes()).toContain('border-danger')` 或
     `toContain('px-3')`——这类断言一旦样式微调或换 Tailwind 类就会产生纯噪音假报错；
   - **严禁无有效断言的空跑用例**：每个 `it` 必须包含对被测行为的实质验证，以下形态一律视为垃圾用例——仅
     `expect(el).toBeDefined()` 式存在性断言、`setProps`/toggle 触发后不验证任何结果、mock（如
     `el.animate`）注入后不做任何断言就结束用例。挂载/执行本身不是测试目的，验证行为才是。
2. **绝对禁写“写死字面量”的脆弱测试（No Hardcoded-Literal Tests）**：
   - **严禁把可变配置常量写死在断言中**：例如严禁在单测中把 `DEFAULT_WORKBENCH_PANEL_ORDER` 默认顺序数组在断言里写死成
     `['analysis', 'variants', ...]`，或断言静态 demo 示例数据里正好有几条记录；
   - **严禁为了迎合坏测试修改业务代码**：当发现测试失败是由硬编码了旧常量、旧字面量导致的假报错时，**严禁反向篡改用户的业务配置去迁就坏测试**，必须直接修正或删除该垃圾测试。
3. **测试价值准入原则（High-Value Testing Only）**：
   - **高价值区（必须单测覆盖）**：乐理与几何算法纯函数（变调、品位坐标计算、和弦推导、AST 标记解析）、跨实例文本编解码协议、数据持久化清洗与备份防丢失守卫、带有内部状态机/手势计算的指令或复合组件；
   - **免测区（严禁编写单测浪费维护成本）**：纯透传 Props 的基础 UI 组件（Icon/Badge/FormRow/Input/SegmentedControl 等）、无内部状态的展示包装层、纯类型定义与导出索引。

## 💡 二、防内卷提醒机制（Self-Check Prompting）

- 若用户提出了带有明显"过度工程化"倾向的模糊重构想法，Agent 应礼貌且坚定地提醒用户：
  > "当前项目架构健康度良好（0 类型错误 / 0 架构违规 /
  > 100% 测试通过）。此项重构预计不会带来可见的运行时或维护性增益，建议优先推进用户已明确规划的产品功能。如确定要执行，请回复确认。"
